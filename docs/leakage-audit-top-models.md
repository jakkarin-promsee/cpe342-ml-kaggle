# Leakage audit of the selected Task 1–5 submission models

Audit date: 15 November 2026. Scope: the five Task columns in `kaggle_t12345_t3log_t5_rankblend25_v17.csv`, traced through v13, v9, and v6 submission cards to their saved model and EDA cards. This is a source-code, artifact, datacard, and read-only data audit. It cannot establish when the competition organizers computed raw features or how they assigned hidden labels.

## Verdict

No direct target, player ID, or exact Train/Test feature-row leakage was found in Tasks 1–3. The Task 4 model consumes only RGB images, and no exact image SHA-256 appears in both Train and Test. The Task 5 file has no labels, so target leakage cannot be tested statistically. **It is not possible to certify that every supplied raw feature is free of temporal or label-generation leakage:** the datacards omit feature extraction timestamps and target-generation rules. The largest unresolved risks are Task 2's inferred tiers, Task 3's spending history and supplied `segment`, and Task 5's four security flags. Task 4's hash grouping does not exclude visually near-identical screenshots.

The selected-model validation scores are also exploratory because some feature/model choices used the same folds or holdout repeatedly. This is selection bias in the estimates, distinct from a target value entering model inputs. Task 5's leaderboard feedback is not an offline F3 validation set.

For the stored Task 1–3 EDA splits, IDs are unique within each split and disjoint across splits. Across all stored predictors, there are **zero exact duplicate feature rows in Train** and **zero exact Train/Test feature-hash overlaps** in each task. Task 4 has **zero exact Train/Test image-hash overlaps**, zero repeated Train hashes, and zero conflicting labels for a Train hash. These checks do not rule out near duplicates or a common latent source.

## Feature-by-feature source inventory

Every input below was checked against the fitted model, EDA formula, and raw datacard. “Raw” means supplied by the competition; it does **not** mean its collection time is verified.

### Task 1: 38 selected inputs

The 30 raw inputs are `kill_death_ratio`, `headshot_percentage`, `win_rate`, `accuracy_score`, `kill_consistency`, `reaction_time_ms`, `account_age_days`, `level`, `level_progression_speed`, `friend_network_size`, `reports_received`, `device_changes_count`, `input_consistency_score`, `avg_session_length_min`, `sessions_per_day`, `night_play_ratio`, `weapon_switch_speed`, `movement_pattern_score`, `aiming_smoothness`, `spray_control_score`, `game_sense_score`, `communication_rate`, `team_play_score`, `buy_decision_score`, `clutch_success_rate`, `first_blood_rate`, `survival_time_avg`, `damage_per_round`, `utility_usage_rate`, and `crosshair_placement`. All are described as gameplay/account measurements in the datacard. No target-like column appears by name. The report count is the most timing-sensitive: the file does not state whether reports were counted before the anti-cheat decision.

The eight derived inputs are `reports_per_100_days` = reports/(account age + 1) × 100; `daily_play_hours` = sessions/day × average minutes/session ÷ 60; `headshot_accuracy_gap` = headshot percentage − accuracy; `aim_precision_mean` and `aim_precision_spread` from the four aim/input scores; `reaction_adjusted_aim` = 100 × aiming smoothness/(reaction time + 1); `aim_strategy_gap` = mean aim score − mean strategy score; and `kd_per_teamplay` = K/D/(team-play score + 0.1). Each is computed within one row. The six excluded engineered columns and raw `map_knowledge` are not selected by the fitted estimator. The threshold is selected in inner CV, but the 38-feature choice was developed during repeated validation work, making its outer-fold estimate somewhat optimistic.

### Task 4: image pixels only

The selected ResNet18 receives the provided Train image's RGB pixel array, resized and padded, plus Train-only random geometry augmentation. Normalization uses fixed pretrained ImageNet constants. Its class label enters the loss only. The training code uses Train paths in fitting; validation paths are used for epoch/variant selection, and Test paths are used for prediction. Exact image-hash grouping protects against byte-identical images across validation folds. ImageNet pretrained weights are explicitly allowed for this task. The 1,228 handcrafted features in the linked EDA card are **not** inputs to this selected model.

## Validation and rule boundary

- Task 1's threshold is fit in inner CV. Its feature-set selection and broader model search consulted related validation folds, so `macro_F2_outer_cv6` is not a fully untouched estimate.
- Task 2's CatBoost preprocessing is fit inside its pipeline on development rows. The 20% holdout has been consulted in later experiments, so model comparisons against it are exploratory.
- Task 3's occurrence, positive amount, and continuous models each refit on all 104,000 labeled Train rows only after development comparisons. The saved `MAE_thb_cv5_procedure` is the earlier procedure estimate, not an evaluation of the full-data fit. Its holdout was reused.
- Task 4's validation uses `image_sha256` as a group. Folds 1–2 selected geometry and fold 3 checked it; the reported three-fold mean includes selection folds. Near-duplicate screenshots remain untested.
- Task 5 has no supervised validation. The written rule forbids Test fitting; the user subsequently reported that the lecturer permits full use of this file for Task 5 modeling and analysis, with a warning against harvesting leaderboard feedback. The two selected detectors in this audit were fit unsupervised on 12,000 unlabeled rows from that file. The public leaderboard informed the final alert budget/rank blend, so its score can be overfit and is not evidence that features are leak-free.

**Practical conclusion:** there is no demonstrated coding leak to remove from the selected models. The unresolved raw-feature timing and Task 5 rule/label provenance cannot be closed from the files supplied. Do not claim “all features have no leakage” in the report; describe the verified code boundaries and these specific limits.
